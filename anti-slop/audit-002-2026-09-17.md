# Anti-slop audit 002 — 2026-09-17

Mode: AFTER

Scope: pemilihan ruangan pada form `dashboard/booking/new` untuk master data 203 ruangan. Tidak ada perubahan source, schema, endpoint, atau logic booking pada tahap audit ini.

## Kontrak yang telah diverifikasi

- `GET /rooms` mengembalikan room aktif, diurutkan menurut lantai lalu nama. Kontrak query yang tersedia: `floorId`, `isSpecialRoom`, dan `search`.
- `GET /rooms/availability?roomId=<id>&startTime=<ISO>&endTime=<ISO>` mengembalikan `{ isAvailable, conflicts }`; konflik yang aman dipakai UI berisi waktu dan status, tanpa identitas peminjam.
- Backend memblokir `PENDING`, `RECOMMENDED`, dan `APPROVED`. Pembuatan booking kembali memeriksa ketersediaan secara atomik dan mengembalikan `409` dengan kode `BOOKING_CONFLICT` bila ada balapan data.
- Rentang API harus berupa ISO dengan offset Jakarta (`+07:00`), sesuai util jadwal publik yang sudah tersedia.

## Temuan

### 1. HIGH — Selector native tidak layak untuk 203 ruangan

- `src/app/(user)/dashboard/booking/new/page.tsx:455-465` merender seluruh room sebagai `<select>` native.
- Tidak ada pencarian nama/kode, filter lantai, pengelompokan lantai, urutan ketersediaan, atau ruang untuk status availability.
- Perbaikan yang diperlukan: combobox terkontrol dengan pencarian case-insensitive, filter lantai, hasil berkelompok, scroll internal, dan navigasi keyboard.
- Aturan terkait: R-03 (responsif), R-26 (interaksi harus berfungsi), dan R-32 (keyboard).

### 2. HIGH — Konflik selector masih berasal dari cache Zustand, bukan endpoint availability

- `src/app/(user)/dashboard/booking/new/page.tsx:154-164` memakai `checkRoomConflict` dari `src/lib/utils.ts` dengan `bookings` dan `academicBlocks` dari store.
- Cache dapat stale dan utility tersebut dapat membangun pesan yang menyebut judul/nama pengguna, sedangkan selector baru harus memakai data aman dari API serta tidak menampilkan detail privat.
- Perbaikan yang diperlukan: gunakan `roomsApi.checkAvailability` sebagai sumber status selector dan cek ulang sebelum submit. Backend tetap sumber kebenaran terakhir.
- Aturan terkait: R-26 dan R-38.

### 3. HIGH — Waktu availability belum memakai format Jakarta eksplisit

- `src/lib/store.ts:228-229` membentuk ISO melalui `new Date(date + 'T' + time).toISOString()`, yang mengikuti zona waktu browser, bukan offset Jakarta secara eksplisit.
- Endpoint availability mem-parsing ISO secara langsung; selector baru harus mengirim `${date}T${time}:00+07:00` agar konsisten dengan util `getJakartaScheduleRange`.
- Perbaikan harus terbatas pada request availability di frontend, tanpa mengubah schema atau aturan backend.
- Aturan terkait: R-26 dan R-31.

### 4. HIGH — Form memilih ruangan dan waktu awal secara otomatis tanpa status API

- `src/app/(user)/dashboard/booking/new/page.tsx:49-52` memilih room pertama, tanggal hari ini, serta `09:00-12:00` bila URL tidak memberikan nilai.
- Keadaan ini berisiko menampilkan pemilihan yang tampak siap diajukan sebelum availability diperiksa.
- Perbaikan yang diperlukan: pertahankan nilai dari query kalender bila ada, namun untuk input yang belum lengkap tampilkan pesan `Pilih tanggal dan waktu untuk melihat ketersediaan` dan jangan mengklaim status tersedia.
- Aturan terkait: R-26, R-27, dan R-38.

### 5. HIGH — Tidak ada state loading, error/retry, maupun toggle availability selector

- Selector saat ini tidak melakukan request availability dan tidak memiliki `Coba Lagi`, toggle `Tampilkan ruangan yang tidak tersedia`, atau empty state sesuai keadaan hasil.
- Tanpa status ini, kegagalan API atau habisnya room tersedia tidak dapat dibedakan dari hasil normal.
- Perbaikan yang diperlukan: state loading, error dengan retry, `Ruangan tidak ditemukan`, dan `Tidak ada ruangan yang tersedia pada waktu tersebut`; room bentrok tampil disabled hanya saat toggle aktif.
- Aturan terkait: R-27 dan R-35.

### 6. MEDIUM — Ringkasan room berisi data di luar kebutuhan selector

- `src/app/(user)/dashboard/booking/new/page.tsx:468-480` merender description dan `PIC` selain nama dan kapasitas.
- Ringkasan yang diminta cukup nama, kode, lantai, kapasitas, dan status availability; tidak ada `Main LT` yang perlu diperkenalkan kembali.
- Perbaikan yang diperlukan: gunakan ringkasan data room yang benar dari API tanpa PIC/description buatan atau data privat.
- Aturan terkait: R-05 dan R-38.

### 7. HIGH — Respons konflik 409 belum menyegarkan availability

- `src/app/(user)/dashboard/booking/new/page.tsx:294-300` hanya menampilkan pesan umum dari error submit.
- Tidak ada deteksi eksplisit `BOOKING_CONFLICT`, refresh availability, atau instruksi memilih room/waktu lain.
- Perbaikan yang diperlukan: hentikan submit, tampilkan pesan spesifik konflik yang aman, panggil ulang availability, dan pertahankan backend sebagai pemeriksaan akhir.
- Aturan terkait: R-26 dan R-27.

### 8. MEDIUM — Endpoint availability bersifat per-room, sehingga 203 request perlu dibatasi

- Kontrak backend yang ada hanya menerima satu `roomId`; tidak ada endpoint batch yang dapat dipakai tanpa perubahan backend.
- Implementasi yang aman perlu membatasi paralelisme, membatalkan/abaikan respons request lama ketika tanggal atau jam berubah, dan tidak memulai pemeriksaan sebelum interval valid.
- Ini menjaga selector responsif tanpa endpoint baru atau dependency baru.
- Aturan terkait: R-03, R-26, dan R-31.

## Batas aman yang akan dipertahankan

- Data room akan tetap berasal dari `GET /rooms`; tidak ada nama, kode, lantai, atau kapasitas hardcoded.
- `Main LT` tidak akan dirender pada selector, hasil, maupun ringkasan.
- Nama master data seperti `Gedung Baru` tidak akan diubah.
- Schema Prisma, data room, endpoint existing, conflict rule backend, grid CBT, dan layout Home tidak menjadi target.
- Tidak ada dependency baru atau commit otomatis.
